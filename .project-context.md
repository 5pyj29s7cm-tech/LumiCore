# LumiOS project context

LumiOS is a local-first, voice-first desktop agent. It is not a frontend-only
virtual OS and not an application launcher. The source of truth for the product
topology is `shared/technical_architecture.ts`; this file is a short contributor
orientation only.

## Current stack

- Client experience: React 19, TypeScript, Vite, Tailwind CSS.
- Native desktop shell: Tauri 2 and Rust.
- Local agent runtime: Node.js, TypeScript, Express.
- Realtime transport: Socket.IO, WebSocket, HTTP.
- Private local data: SQLite plus a dedicated user-data directory.
- Capability system: CapabilityManifest, built-in tools, MCP, reviewed Skills.
- Cognition: model-role routing, CapabilityPlan, TaskLedger, verification.
- Voice: streaming STT/TTS, voiceprint, barge-in, meeting capture.
- Native automation: one shared contract with Windows UI Automation and macOS
  Accessibility adapters.

## Architectural invariants

- Capability definitions are shared by Windows and macOS; native adapters differ.
- Tool discovery, routing, permission, risk, evidence, execution, verification,
  diagnostics, and self-awareness consume the same CapabilityManifest.
- Client surfaces and actions come from `shared/client_surfaces.ts`.
- A task is complete only when its ledger contains execution evidence and the
  required verification succeeds.
- User memory, configuration, generated drafts, logs, and migration backups must
  not be stored in the source tree.

## Main source areas

- `src/`: React clients and voice hooks.
- `src-tauri/`: native shell and platform commands.
- `server/cognition/`: intent, planning, task ledger, verification, finalization.
- `server/tools/`: capability definitions, manifest, policy, execution engine.
- `server/mcp/` and `server/skills/`: MCP and reviewed skill lifecycle.
- `server/external_control/`: shared native automation contract and adapters.
- `shared/`: cross-runtime registries and architecture contracts.

Do not add a new route, permission list, client action alias, or success heuristic
when an existing manifest/registry/ledger field can express the requirement.
